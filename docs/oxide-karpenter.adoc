= Karpenter Provider Oxide
:description: Example NodePool and OxideNodeClass configurations for common Oxide workloads.

[.lead]
Karpenter Provider Oxide launches Kubernetes nodes on an Oxide rack. A `NodePool`
describes when and how Karpenter should add capacity; its referenced `OxideNodeClass`
describes how that capacity is launched on Oxide.

The examples below are complete pairs. Replace values written as `<PLACEHOLDER>`, then
apply a pair with `kubectl apply -f`.

[NOTE]
====
Each `OxideNodeClass` selects exactly one bootstrap provider. Use `kubeadm` for a
kubeadm-managed cluster or `rke2` for an RKE2 cluster.
====

[id="general-purpose"]
== 1. Flexible general-purpose workers

Use one dynamic pool for ordinary stateless workloads. Karpenter chooses the smallest
available Oxide instance shape that satisfies each pending pod, while the pool-wide
limits and disruption settings bound its growth and replacement behavior.

This example demonstrates:

* dynamic, workload-driven scaling;
* aggregate CPU and memory limits;
* consolidation of empty or underutilized nodes;
* kubeadm bootstrap; and
* selection of an Oxide image and VPC by ID and name.

[source,yaml]
----
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: general-purpose
spec:
  limits:
    cpu: "128"
    memory: 512Gi
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    consolidateAfter: 1m
  template:
    metadata:
      labels:
        workload-tier: general-purpose
    spec:
      expireAfter: 720h
      nodeClassRef:
        group: karpenter.oxide.computer
        kind: OxideNodeClass
        name: general-purpose
      requirements:
        - key: kubernetes.io/arch
          operator: In
          values: [amd64]
        - key: kubernetes.io/os
          operator: In
          values: [linux]
---
apiVersion: karpenter.oxide.computer/v1alpha1
kind: OxideNodeClass
metadata:
  name: general-purpose
spec:
  bootstrap:
    kubeadm: {}
  kubeletArgs:
    - cloud-provider=external
  storage:
    boot:
      size: 40Gi
  imageSelector:
    - id: <IMAGE_ID>
  subnetSelector:
    - project: <OXIDE_PROJECT>
      vpcName: <OXIDE_VPC>
----

Pods can opt into this pool with `nodeSelector: {workload-tier: general-purpose}`.
Pods without that selector may also use it if no other scheduling constraint excludes it.

[id="storage-workers"]
== 2. Storage-isolated RKE2 workers

Use a dedicated pool when a workload needs data disks or should not share nodes with
general-purpose pods. The taint reserves the nodes for pods that explicitly tolerate it.
The node class adds two local cache disks and a read-only distributed disk created from
an existing snapshot.

This example demonstrates:

* RKE2 bootstrap using a token stored in a Kubernetes `Secret`;
* labels and taints for workload isolation;
* multiple local disks mounted beneath a directory; and
* a distributed data disk restored from a snapshot and mounted read-only.

Create the RKE2 token before applying the pair:

[source,console]
----
kubectl create secret generic rke2-agent-token \
  --namespace karpenter \
  --from-literal=token='<RKE2_AGENT_TOKEN>'
----

[source,yaml]
----
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: storage-workers
spec:
  limits:
    cpu: "64"
    memory: 256Gi
  template:
    metadata:
      labels:
        workload-tier: storage
    spec:
      nodeClassRef:
        group: karpenter.oxide.computer
        kind: OxideNodeClass
        name: storage-workers
      requirements:
        - key: kubernetes.io/arch
          operator: In
          values: [amd64]
        - key: kubernetes.io/os
          operator: In
          values: [linux]
      taints:
        - key: dedicated
          value: storage
          effect: NoSchedule
---
apiVersion: karpenter.oxide.computer/v1alpha1
kind: OxideNodeClass
metadata:
  name: storage-workers
spec:
  bootstrap:
    rke2:
      tokenRef:
        name: rke2-agent-token
        namespace: karpenter
        key: token
  kubeletArgs:
    - cloud-provider=external
  storage:
    boot:
      size: 40Gi
    diskSets:
      - name: cache
        type: Local
        count: 2
        size: 200Gi
        filesystem: xfs
        mountDir: /var/lib/cache
      - name: dataset
        type: Distributed
        size: 500Gi
        snapshotSelector:
          - name: production-dataset
            project: <OXIDE_PROJECT>
        readOnly: true
        mountPath: /opt/dataset
  imageSelector:
    - name: <RKE2_IMAGE_NAME>
      os: ubuntu
      project: <OXIDE_PROJECT>
  subnetSelector:
    - project: <OXIDE_PROJECT>
      vpcName: <OXIDE_VPC>
----

Workload pods need both `nodeSelector: {workload-tier: storage}` and this toleration:

[source,yaml]
----
tolerations:
  - key: dedicated
    operator: Equal
    value: storage
    effect: NoSchedule
----

The image must provide the filesystem tools used by the configuration (`xfsprogs` in
this case). Snapshot-backed disks retain their existing filesystem and are not formatted.

[id="spread-ingress"]
== 3. Fixed ingress capacity spread across sleds

Use a static pool when a service should always have a known number of nodes. This pool
keeps three ingress workers. Its node class creates and owns an Oxide anti-affinity group,
so the rack refuses a launch rather than placing two of these instances together when the
placement constraint cannot be satisfied. Each node also receives an IPv4 address from a
named IP pool.

This example demonstrates:

* a fixed-size NodePool;
* a provider-managed Oxide anti-affinity group;
* strict placement with `policy: fail`;
* ephemeral external IP allocation; and
* selection of an SSH key for break-glass access.

[source,yaml]
----
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: ingress
spec:
  replicas: 3
  limits:
    nodes: 3
  template:
    metadata:
      labels:
        workload-tier: ingress
    spec:
      nodeClassRef:
        group: karpenter.oxide.computer
        kind: OxideNodeClass
        name: ingress
      requirements:
        - key: kubernetes.io/arch
          operator: In
          values: [amd64]
        - key: kubernetes.io/os
          operator: In
          values: [linux]
      taints:
        - key: dedicated
          value: ingress
          effect: NoSchedule
---
apiVersion: karpenter.oxide.computer/v1alpha1
kind: OxideNodeClass
metadata:
  name: ingress
spec:
  bootstrap:
    kubeadm: {}
  kubeletArgs:
    - cloud-provider=external
  storage:
    boot:
      size: 30Gi
  affinity:
    managed:
      type: AntiAffinity
      policy: fail
  ephemeralIPs:
    - pool:
        name: <EXTERNAL_IPV4_POOL>
  sshKeySelector:
    - name: <SSH_KEY_NAME>
  imageSelector:
    - id: <IMAGE_ID>
  subnetSelector:
    - project: <OXIDE_PROJECT>
      vpcName: <OXIDE_VPC>
----

Ingress pods should select `workload-tier: ingress` and tolerate the `dedicated=ingress`
taint. Because placement is strict, this configuration intentionally leaves a replica
pending if the rack cannot honor the anti-affinity request.

[id="check-status"]
== Check the result

An `OxideNodeClass` must become `Ready` before Karpenter can use it. Check both resources
after applying an example:

[source,console]
----
kubectl get oxidenodeclasses
kubectl get nodepools
kubectl get nodeclaims
----

If a node class is not ready, its conditions identify unresolved images, subnets,
snapshots, IP pools, SSH keys, bootstrap configuration, or storage configuration:

[source,console]
----
kubectl describe oxidenodeclass <NODECLASS_NAME>
----
